# 团队积分与团队管理方案（2026-10-23）

> 本文回答六个问题：① 积分套餐怎么设计 ② 积分怎么消耗 ③ 余额在哪看 ④ 哪些场景消耗 ⑤ 团队功能怎么开通
> ⑥ 配套管理功能与批量操作清单、角色权限边界。
>
> **基线**：v1.5.94 已上线团队主体 / 成员 / 团队记忆（MemHub）/ 团队知识库（WeKnora）/ 团队套餐（席位+容量+赠分）/ 团队积分池（只进不出）。
> 本文在既有实现上补「积分收支闭环」与「按用户开通 + 批量管理」。凡与现状冲突处，第 11 节给迁移路径。

---

## 0. 先划清三个概念（否则后面全会串）

| 概念 | 是什么 | 谁付费 | 存放在哪 | 现有/新增 |
|---|---|---|---|---|
| **个人积分** | 个人账户余额，买个人套餐 / 个人能力 | 个人（充值） | `db.points[username]` | 现有，**与团队完全隔离** |
| **团队套餐** | 订阅制商品：买的是**席位 + 容量 + 每月积分**，按天计期 | 团队 owner 付钱 | `db.teamPlans` + `db.teamEntitlements` | 现有，本轮扩展 |
| **团队积分** | 团队内流通的计量单位，**只能团队能力消耗**，不能提现、不能转个人 | 团队（买积分包 / 套餐赠送 / 管理员发放） | `db.teamPointsLedger`（流水即账本） | 现有表，本轮补消耗 |

三条硬边界（写进代码断言）：

1. 团队积分 **不能** 支付个人套餐；个人积分 **不能** 支付团队套餐或团队能力。
2. 团队积分 **没有** 「转给个人」接口（避免洗积分与对账黑洞）。
3. 团队积分余额 **只由流水求和**得出，不单独存冗余数字（`team.pointsPool` 只是镜像，仅供列表展示）。

## 1. 数据模型（新增 / 变更）

### 1.1 团队能力开通（新增，第 5 节的核心）

```js
db.teamAccess[username] = {
  enabled: true,              // 是否已开通（未开通 = 看不到入口、接口 403）
  grantedBy: "admin",         // 谁开的
  grantedAt: 1792770000000,
  expiresAt: 0,               // 0 = 长期；>0 = 试用/限期
  maxTeams: 1,                // 可创建/加入的团队数上限（默认 1，管理员可放大）
  note: "首批试点",            // 备注（管理端可见）
  revokedAt: 0, revokedBy: "",// 关闭留痕（不删记录，便于审计与恢复）
}
```

### 1.2 团队积分套餐（新增，两小类）

```js
// ① 积分充值包：纯积分，随时买，不绑席位
db.teamPointPkgs[pkgId] = {
  id, name, desc, active, sort,
  priceCny,        // 售价（元）
  points,          // 到账积分（基础）
  bonusPoints,     // 额外赠送（促销用；展示为「+N」）
  validDays,       // 积分有效期（0 = 永久；>0 时按批次记到期）
  limitPerTeam,    // 每团队累计限购次数（0 = 不限）
}

// ② 席位套餐：就是现有 db.teamPlans，本轮加两个字段
db.teamPlans[planId] = {
  ...现有字段（priceCny / points / seats / days / kbQuotaMb / memQuotaMb）,
  monthlyPoints,   // 【新增】有效期内每月自动补充的积分（0 = 不补）
  overagePolicy,   // 【新增】配额用尽后："block"（拒绝，默认）| "pool"（继续扣余额）
}
```

> 为什么分两类：席位套餐是**订阅**（周期性、带额度和容量），积分包是**预付费**（一次性、可叠加、可用于超额）。
> 混成一张表会让「续费」「过期」两套语义打架，也让后台两个表单互相污染（个人套餐与自己踩过同样的坑）。

### 1.3 团队积分账本（现有表，扩字段与 kind）

```js
db.teamPointsLedger[teamId][rowId] = {
  id, at, teamId,
  delta,        // + 入账 / - 消耗
  kind,         // plan-bonus | pkg-buy | admin-grant | monthly-quota |
                // consume | refund | expire
  scene,        // 【新增】消耗场景（见 §4）：kb_search | kb_upload | memory_write | ...
  ref,          // 幂等键：同一 ref 只入账一次（回调/重试/双击都靠它）
  note, actor,
  period,       // 【新增】'2026-10'（月度配额专用，便于按月汇总与清零）
}
```

### 1.4 团队积分配额（新增，按周期）

```js
db.teamQuota[teamId] = {
  period: "2026-10",   // 当前周期
  total: 5000,         // 本期配额总量（来自套餐 monthlyPoints）
  used: 1200,          // 本期已消耗
  resetAt: 1793400000000,
}
```

### 1.5 策略扩字段（现有 `db.teamPolicy`）

```js
db.teamPolicy = {
  ...现有（enabled / freeSeats / memoryEnabled / kbEnabled / maxEntryChars）,
  accessRequired: true,      // 【新增】创建团队是否需要管理员逐个开通（第 5 节）
  pointsEnabled: true,       // 【新增】团队积分体系总开关
  prices: {                  // 【新增】各场景单价（管理员可调，0 = 该场景免费）
    kb_search: 1,            // 点/次
    kb_upload: 2,            // 点/MB（向上取整）
    memory_write: 1,         // 点/条（P1，客户端上报）
    memory_search: 1,        // 点/次（P1）
  },
  lowBalanceWarn: 200,       // 【新增】低于此值在页面顶部提示
}
```

## 2. 一、团队积分套餐设计

### 2.1 套餐类型（三档，覆盖「小团队试水 → 部门级」）

| 类型 | 商品 | 售价示例 | 席位 | 容量 | 积分 | 适合 |
|---|---|---|---|---|---|---|
| **试用/免费档** | 无（开通即可） | ¥0 | 3 | 0（不限） | 0（不可消耗，仅记录） | 验证流程 |
| **席位套餐（订阅）** | 月卡 / 季卡 / 年卡 | ¥99 / ¥269 / ¥899 | 5 / 10 / 30 | KB 2G / 4G / 20G，记忆 1G / 2G / 10G | 每月 3000 / 8000 / 50000 | 常规项目组 |
| **积分充值包（预付费）** | 小包 / 中包 / 大包 | ¥50 / ¥200 / ¥800 | — | — | 5000 / 22000 / 100000（含赠送） | 超额、临时冲刺 |

### 2.2 额度来源与到账方式（关键区别）

| 来源 | 到账形态 | 是否过期 | 触发 | 流水 kind |
|---|---|---|---|---|
| 席位套餐首购/续费 | **一次性**入余额 + 当月配额生效 | 余额按 `validDays`；配额按月清零 | 支付回调 / 管理员手动开通 | `plan-bonus` |
| 席位套餐有效期内的每月额度 | 进 `teamQuota`（**不是余额**） | **当月清零，不结转** | 每月 1 日 00:05 定时补 | `monthly-quota` |
| 积分充值包 | 入余额（按批次记到期） | 按包 `validDays` | 支付回调 / 管理员补单 | `pkg-buy` |
| 管理员分配 | 入余额 | 0（长期）或按管理员指定 | 管理端「分配积分」（支持批量） | `admin-grant` |

> **设计取舍**：月度配额「当月清零」而不是结转。理由：订阅制里配额是「这个月能用多少」，结转会让成本不可预测；
> 而充值包是「买断的点数」，必须长期有效。两者混在一起算余额，团队会误以为配额可以攒。

### 2.3 配置方式（管理端）

**位置**：管理组 →「团队管理」→ 第三个板块「团队积分」

三个子卡：

1. **积分场景与单价**：`kb_search` / `kb_upload` / `memory_write` / `memory_search` 四个输入框（点/次、点/MB），
   加「低余额提醒阈值」「积分体系总开关」。保存即生效（下一次调用按新价扣）。
2. **积分充值包**（表 + 表单）：名称 / 售价 / 到账积分 / 赠送积分 / 有效期（天）/ 限购次数 / 上下架 / 排序。
3. **席位套餐**（沿用现有表，新增两列）：每月积分（`monthlyPoints`）、超额策略（拒绝 / 转扣余额）。

字段校验（服务端，全部走白名单）：
- 金额 `0 ≤ priceCny ≤ 100000`，保留 2 位；积分 `0 ≤ points ≤ 10,000,000`；有效期 `0 ≤ validDays ≤ 3650`。
- 上下架切换请求只带 `{id, active}` ⇒ **合并现值**，不允许整单覆盖（否则一次 toggle 清空 features/价格）。

## 3. 二、团队积分消耗逻辑

### 3.1 消耗规则

1. **单位**：积分是整数，最小 1 点；计算后 `Math.ceil`（不足 1 点按 1 点，避免 0.3 点无法记账）。
2. **计价**：按场景单价 × 量。检索 = 1 次 × 单价；上传 = `ceil(字节 / 1MB)` × 单价。
3. **前提**：团队套餐在有效期内（`teamEntitlements.status === "active"`）且积分体系开启。过期团队 **只读**：
   检索仍可（免费额度内），上传与写入拒绝并提示续费（P1 的「到期降级」在这里落地）。
4. **不计费**：开通空间、建库、发凭据、成员管理、套餐购买本身 —— 这些是**平台运维动作**，不该被积分卡住。

### 3.2 扣减顺序（唯一顺序，写进函数注释）

```
① 本期配额 teamQuota（当月有效，先扣快过期的）
      ↓ 不足
② 余额（按「最早到期优先」批次：validDays 越早到期越先扣；永久批次最后）
      ↓ 不足
③ 按套餐 overagePolicy：
     "block" → 402 points-insufficient（前端提示充值/升级）
     "pool"  → 同上（pool 与 block 的区别只在「有无余额」，无余额时都拒绝）
```

实现上把 ① 与 ② 合成一个「可用总额」判定，但**记账分开**：一次消耗可能产生两行流水
（`consume` 配额 + `consume` 余额），都带同一个 `ref`，前端只显示合计。

### 3.3 事务边界与幂等

- **判定与扣减之间不允许 `await`**（Node 单线程下即天然原子）。流程固定为：
  `校验权限 → 校验额度 → 写流水（本地） → persist() → await 上游调用 → 失败则写 refund 流水`。
- **幂等键 `ref`**：`<scene>:<teamId>:<业务 id>`。同 ref 已存在则直接返回上次结果，不重复扣。
  例：`kb_search:T123:req-8f21`（前端每次检索带一个随机 reqId，重试安全）。
- **退分**：上游失败/超时必须写 `refund`（`delta > 0`，`kind: "refund"`，`ref` 与消耗同键 + `:refund`），
  余额恢复。退分失败只记日志不阻断响应（下次对账脚本 `verify` 会发现）。

### 3.4 失败处理矩阵

| 失败类型 | HTTP | error | 是否扣过 | 处理 |
|---|---|---|---|---|
| 未开通团队（无 access） | 403 | `team-access-denied` | 否 | 引导联系管理员 |
| 非团队成员 | 403 | `not-a-member` | 否 | — |
| 能力未开通（KB/记忆） | 403 | `team-kb-disabled` | 否 | 引导 owner 开通 |
| 套餐过期 | 402 | `team-plan-expired` | 否 | 只读模式提示续费 |
| 积分不足 | 402 | `points-insufficient` | 否 | 返回缺口数 `{need, available}`，前端一键去充值 |
| 同 ref 重复请求 | 200 | — | 否（幂等命中） | 返回原结果 |
| 上游超时/5xx | 502 | `upstream-failed` | **是 → 已退** | 响应带 `refunded: true` |
| 上游 409（同名文件） | 409 | `duplicate-file` | **是 → 已退** | 人话提示改名 |
| 限流 | 429 | `rate-limited` | 否 | 响应带 `retryAfter` |
| 并发超额（双请求同时过校验） | 409 | `points-race` | 否 | 客户端重试一次（幂等键保证安全） |

> 「先扣后退」是有意的：**宁可多退一笔，也不让用户白用**。反过来的「先调后扣」会在上游慢时产生负余额。

## 4. 三、团队积分余额的展示

### 4.1 展示口径（必须统一，四端一致）

```
可用积分 = 本期配额剩余（total - used） + 永久余额 + 未到期余额
冻结积分 = 0（当前无冻结机制；P2 若加「进行中的上传」才需要）
已用（本月） = 本周期消耗合计（配额 + 余额，按 period 汇总）
```

### 4.2 展示位置（5 处，各有分工）

| 位置 | 展示内容 | 刷新时机 | 面向 |
|---|---|---|---|
| **团队概览 hero**（主位） | 大号「可用 8,240 积分」+ 小字「本月已用 1,760 · 配额剩 3,240 · 余额 5,000」+「充值」按钮 | 进入页面 / 消耗后返回 | owner、admin、member 都可见 |
| **侧栏「团队」组标题旁** | 小号数字 `8.2k`（仅当前团队） | 切团队 / 每 60s | 全体（一眼可见，不占版面） |
| **团队知识库页顶部** | 「本次检索消耗 1 点 · 可用 8,240」 | 每次检索后 | 操作者 |
| **团队设置 → 团队套餐卡** | 套餐名 / 到期 / 每月配额 / 配额已用 / 余额 / 最近 5 条流水 | 进入页面 | owner |
| **管理端「团队管理 → 团队列表」** | 每行「积分余额 / 本月消耗 / 套餐」三列（可排序，找异常团队） | 进入页面 | 平台管理员 |

### 4.3 展示规则（防误解）

- **不复用个人积分的组件**：团队余额的文案必须带「团队」二字（`团队可用积分`），避免与个人余额混淆。
- 余额 ≤ `lowBalanceWarn` 时：数字变橙 + 一行「余额偏低，<a>去充值</a>」；= 0 且配额耗尽时变红 + 阻断提示。
- 余额为 0 但配额仍有：**不告警**（配额是套餐给的，属正常）。
- 千分位分隔；超 10 万显示 `12.3 万`。
- **不给未开通团队的用户任何入口**（第 5 节），所以也不存在「余额 0 的空壳页」。
- 个人视图（用户中心 / 订阅中心）**永远不显示**团队积分。

## 5. 四、消耗场景与触发流程

### 5.1 可计量场景（经过云端的才算，这是硬约束）

| # | 场景 | 触发动作 | 计量 | 单价默认 | 谁付费 | 阶段 |
|---|---|---|---|---|---|---|
| 1 | `kb_search` | 团队知识库页检索 / 成员工具走云端代理 | 次 | 1 | 团队 | **P0（现在就通）** |
| 2 | `kb_upload` | 团队知识库页上传 / 工具上传 | MB（向上取整） | 2 | 团队 | **P0** |
| 3 | `memory_write` | 成员 Codex 写团队记忆 | 条 | 1 | 团队 | P1（需客户端上报） |
| 4 | `memory_search` | 成员 Codex 检索团队记忆 | 次 | 1 | 团队 | P1（需客户端上报） |
| 5 | `ai_call` | 团队内调用模型 | 1k tokens | 10 | 团队 | P2（需网关计量） |
| 6 | 团队套餐购买 | owner 下单 | — | — | **钱**（不进积分） | 现有 |
| 7 | 开通空间 / 建库 / 发凭据 | owner 点开通 | — | 0 | — | 现有 |

> **为什么 3/4 只能 P1**：团队记忆的内容在 MemHub，成员的工具**直连** MemHub（云端只发凭据），
> 云端看不到调用量 ⇒ 无法计量。要么客户端上报用量（需要桌面端 `scope` 参数一起做），要么不做。
> 本轮方案里默认 **P0 只对 1、2 收费**，3/4 先按「免费但记次数」（只写 `scene` 流水 `delta: 0`），
> 等上报通道落地再改价 —— 这样后台数据能提前积累，改价时不用从零开始。

### 5.2 触发流程（以 kb_search 为例，含退分）

```
前端                云端                                    上游(WeKnora)
 │  POST /teams/:id/kb/search {query, reqId}
 ├──────────────────►│
 │                   │ 1 鉴权：access → 成员 → 能力开关 → 套餐有效期
 │                   │ 2 限流：30 次/分/人
 │                   │ 3 计价：need = 1 × price.kb_search
 │                   │ 4 额度：quota 剩余 + 余额 ≥ need ?
 │                   │ 5 扣减：写 consume 流水（ref=kb_search:tid:reqId）→ persist
 │                   │ 6 调用 ──────────────────────────────►│
 │                   │ ◄──────────────────── hits / error ───┤
 │                   │ 7 失败 ⇒ 写 refund 流水（同 ref + :refund）
 │ ◄─────────────────┤ 200 {hits, cost:1, points:{available}}
```

上传路径额外一步：**先查容量**（`kbUsedMb + mb ≤ kbQuotaMb`）再扣积分 —— 容量和积分是两道不同的闸，
顺序固定为「容量 → 积分」，因为容量超了扣积分没意义。

### 5.3 配额月度补充流程

```
每月 1 日 00:05（服务端定时器，进程启动时补跑一次断档）
  对每个 status=active 且套餐有 monthlyPoints 的团队：
     teamQuota[teamId] = { period: 本月, total: monthlyPoints, used: 0, resetAt: 下月 1 日 }
     写流水 monthly-quota（delta: 0，note 记「本月配额 5000」——它是配额不是余额，不改余额）
  过期未续费的团队：不再补配额（只读）
```

## 6. 五、团队功能的开通机制（本次最重要的行为变更）

### 6.1 现状与目标

| 项 | 现状（v1.5.94） | 目标 |
|---|---|---|
| 谁能建团队 | **任何登录用户**（只要总开关开） | **仅被管理员开通 `teamAccess` 的用户** |
| 团队入口 | 侧栏「团队」组**全量可见** | **未开通：整组不渲染**；已开通才出现 |
| 管理员团队页 | 管理员可见 | 不变（管理员组本来就按角色隐藏） |

### 6.2 三道闸门（顺序不可颠倒）

```
闸 1 平台总开关   db.teamPolicy.enabled        关 ⇒ 所有人（含已开通）都 403 team-disabled
闸 2 用户级开通   db.teamAccess[user].enabled  关/无记录 ⇒ 403 team-access-denied（入口不渲染）
闸 3 团队级开通   db.teamIntegrations 已建库/空间  关 ⇒ 该团队 KB/记忆接口 409（其他功能可用）
```

> 闸 2 与闸 1 的分工：闸 1 是「产品级事故开关」（出事一键关停所有人），闸 2 是「商务/试用控制」（谁能用）。
> 两者都开才可用；**关闸 2 不影响已建团队的数据**，重新开通后原样恢复。

### 6.3 开通后才有 / 关闭后失去（前端 + 后端双保险）

| 能力 | 未开通 | 已开通 |
|---|---|---|
| 侧栏「团队」组 | **不渲染**（`navGroupTeam.hidden = true`，直接移除更彻底） | 渲染 5 个页面 |
| `/teams` 列表 / 详情 / 成员 / 积分 | 403 `team-access-denied` | 正常 |
| 创建团队 | 403 | 允许（受 `maxTeams` 限制） |
| 用邀请码加入 | 403（提示「请先联系管理员开通团队功能」） | 允许 |
| 管理端「团队管理」 | 仅平台管理员（与团队开通无关） | 同 |

**双保险**：前端隐藏入口只是体验；服务端每个 `/teams/*` 都先校验 `teamAccess`，前端被绕过也进不来。

### 6.4 开通方式（管理员）

1. **单个开通**：管理端「团队管理 → 开通与权限」表格，每行一个开关 + 「有效期」「备注」两列。
2. **批量开通**：勾选多个用户 → 「批量开通」（见 §7.2）。
3. **按条件批量**：粘贴用户名列表 / 上传 CSV / 「选中某套餐的购买者」三种选人方式。
4. **开通通知**：开通后在用户下次登录时弹一次提示（「管理员已为你开通团队功能，去创建团队」），
   用 `db.teamAccess[user].notifiedAt` 去重，不重复弹。

### 6.5 关闭（回收）语义

- 关闭 = `enabled: false`，**不删记录、不删团队**。用户立刻失去入口与接口；其创建/加入的团队保留（其他成员不受影响）。
- 若关闭的是团队 owner：团队进入「无人管理」状态，管理端列表高亮，提示「owner 团队功能已关闭，请指派新 owner」。
- 关闭不退款（团队套餐是团队资产，与个人开通状态解耦）—— 这点必须写在管理端按钮的二次确认里。

### 6.6 迁移（存量数据）

- 上线时执行一次 backfill：**当前所有团队的 owner 与 active 成员**自动写入 `teamAccess.enabled = true`，
  `grantedBy: "migration"`, `note: "存量成员自动开通"`。
- 存量未参与团队的普通用户：不写记录（= 未开通），与目标一致。
- 结果：现有 3 人团队上线后无人被踢出，新用户默认需要管理员开通。

### 7.2 批量操作（必须配齐的 6 个）

统一交互模型（所有批量操作共用，避免各写一套）：

```
选人/选团队 → 预览（dry-run：将影响 N 个对象，列出前 20 条）→ 确认 → 逐条执行 → 结果报告
                                                               ↑ 单条失败不中断，汇总成功/失败清单
```

| # | 批量功能 | 输入 | 语义 | 结果页 | 适用角色 |
|---|---|---|---|---|---|
| B1 | **批量开通团队功能** | 用户名列表（换行/逗号）/ CSV / 勾选表格 | 逐个写 `teamAccess.enabled=true`，同一个有效期与备注 | 成功 N / 已开通 N（跳过）/ 不存在 N（列名单） | 平台管理员 |
| B2 | **批量关闭** | 同上 | `enabled=false`，保留记录 | 成功 / 未开通（跳过） | 平台管理员 |
| B3 | **批量分配积分** | 团队列表（勾选）+ 积分数量 + 原因 | 每个团队写一条 `admin-grant` 流水（ref=`batch:<taskId>:<teamId>` 幂等） | 成功 N / 失败（含原因） | 平台管理员 |
| B4 | **批量管理成员**（加/移/改角色） | 团队 + 用户名列表 + 动作 | 加：受席位上限约束，超限的**逐条失败并说明**（不自动扩容）；移：不影响其贡献内容；改角色：admin↔member | 每条结果（含「席位已满」） | 团队 owner / admin（admin 不能改角色） |
| B5 | **批量设套餐** | 团队列表 + 套餐 ID | 等价于逐个 `grant`（席位/容量立即生效，赠分按次） | 成功 / 套餐不存在 | 平台管理员 |
| B6 | **批量导出** | 团队列表（勾选/全选） | 导出 CSV：团队/owner/席位/套餐/到期/积分余额/本月消耗/空间状态 | 直接下载 | 平台管理员 |

**批量执行的工程约束**（不做会出事）：

- **限流**：每批 ≤ 200 条；同一管理员每分钟 ≤ 3 批。
- **任务化**：`db.adminTasks[taskId] = { type, total, done, ok, failed[], createdAt, by, status }`，
  前端轮询任务进度（避免 500 条同步请求超时）。
- **单条隔离**：一条失败不影响其余（`try/catch` 包裹）。
- **幂等**：`taskId + 对象 id` 作为 ref，重试不会重复加积分。
- **审计**：`db.adminAudit[]` 记录谁在何时对哪些对象做了什么（批量也逐条记，便于追溯）。
- **二次确认文案**必须写清影响面：「将为 37 个团队各加 5000 积分（合计 185,000）」。

## 12. 三个容易踩的坑（提前写下来）

1. **扣了分但没调用**：`persist()` 在调用上游前就落盘，进程若在此刻被 kill，钱扣了、活没干。
   缓解：`refund` 兜底 + 每日对账脚本（找「有 consume 无 success 标记」的流水，超过 10 分钟的自动退）。
2. **配额与余额混算**：前端只显示合计会导致「配额用完了但余额还有」时用户困惑。必须分项展开（§4.2）。
3. **批量开通无 dry-run**：一次性给 500 人开通、给 37 个团队各发 5 万分，误操作不可逆。
   所以 §7.2 强制「预览 → 确认 → 结果报告」，且积分发放必须填原因。

### P1 审查修复（本轮）

1. 🔴 **CSV 公式注入**：审计导出把管理员/备注直接拼进 CSV，Excel 会执行以 `= + - @` 开头的单元格（备注是管理员自由文本）。改为统一 `csvCell()`：加引号转义 + 危险前缀补 `'`。
2. 🟡 **审计无界增长**：上限裁剪原先只写在「开通/关闭」路径，发积分 / 批量 / 开通套餐三处无裁剪。抽 `auditPush()` 统一处理。
3. 🟡 **「本月已用」与配额矛盾**：月中升级会把 `quota.used` 清零，而 monthUsed 仍按整月累计 ⇒ 出现「已用 10,055 / 配额 5,000 却剩 5,000」。加 `quota.startedAt` 作本期起点，文案改「本期已用」（存量数据补 startedAt）。
4. 🟡 **`db.topups` 未初始化崩溃**：全新实例从未充值过时，团队下单写 `db.topups[id]` 抛 500。补 `(db.topups || (db.topups = {}))`。
5. Nit：`team-grant-plan` 未翻译（页面显示原始动作名）→ 补「开通团队套餐」。
